自作の skill(input-ontology-map)で、3 つの領域をオントロジーマップ(概念図)で表現してみました。出典はどれも一次情報だけで、Git は同梱のマニュアル、AWS は公式ドキュメント(docs.aws.amazon.com)です。先に 3 枚の成果物から評価した結論を書き、そのあと図を 1 枚ずつ載せます。

| 図 | 対象 | 概念 | 関係 | 出典 |
| --- | --- | --- | --- | --- |
| Git の用語 | index・HEAD・reset の 3 モードなど | 18 個 | 29 本 | man ページ 6 つ |
| AWS の VPC とネットワーク | VPC・NAT ゲートウェイ・VPC エンドポイントなど | 22 個 | 32 本 | 14 ページ |
| AWS の非同期メッセージング | SNS・SQS・EventBridge | 19 個 | 25 本 | 12 ページ |

図の読み方は 3 枚とも同じです。

- 箱が概念、線が関係です。線には「先端のコミットを指す」のような述語が書いてあり、色は 6 種類の関係カテゴリ(is-a・part-of・depends-on・produces・constrains・relates-to)を表します
- 箱を押すと右の「詳細」に定義・別名・出典が出ます
- 右の「問い」タブで問いの名前を押すと、答えに使う概念が図の上で強調されます
- 左下の「Action / Policy を重ねる」を入れると、操作が図に重なり、各操作がどの概念を書き換えるかが線で出ます

## オントロジーマップの評価

下に載せる 3 枚から、オントロジーマップという方法そのものを評価します。

結論から書くと、オントロジーマップは初めて学ぶ領域の、インプットの道具として役に立ちます。役に立つのは次の 3 つです。

1. 用語の整理
   - 別名を 1 つの箱にまとめ、同じ名前の別物は箱を分ける。Git の index・staging area・cache は 1 つの箱になり、SQS と SNS の「リドライブポリシー」は 2 つの箱になった
2. 領域の中の知識どうしの関係
   - 1 つの領域の中で、概念がどうつながるかを線で追える。`git reset` の 3 モードが、ブランチヘッド・index・作業ツリーのどこまでを書き換えるかが線の本数で分かる
3. 周辺の知識との関係
   - 領域の外にある概念とのつながりも図に入る。SNS の DLQ の実体は SQS キューで、パブリックサブネットかどうかはサブネットではなくルートテーブルの中身で決まる

学んだあとに、サービスを選ぶ・設計を決めるといった判断の道具にはなりません。判断の基準は出典に書かれていない限り図に入らないからです。以下のメリットとデメリットは、この結論の根拠です。

- メリット
  1. 用語の混乱を解消できる
     - 別名は 1 つの箱にまとめ、同じ名前で別のものは箱を分けるので、名前と実体の対応が図の上で決まる。SQS と SNS の「リドライブポリシー」は 2 つの箱になり、Git の index は 5 通りの書かれ方が 1 つの箱になった
  2. 図が大きくなりすぎない
     - 先に問いを決めて、答えに要る概念だけを入れる。3 枚とも概念は 18〜22 個に収まった
  3. どこまで信用できるかが分かる
     - 関係ごとに出典が付き、原文にない関係には「推定」の印が付く
  4. 問いから図を読める
     - 問いを押すと答えに使う概念が強調され、Action を重ねると操作が何を書き換えるかを線で追える
- デメリット
  1. 出典に書かれたことしか入らない
     - 「EventBridge と SNS のどちらを選ぶか」のような判断基準は、公式ドキュメントに無いので図にも入らなかった
  2. 問いの外は落ちる
     - Transit Gateway や IPv6 は問いに要らないので外した。領域全体を網羅した地図にはならない
  3. 作るのに出典を読む工程が要る
     - 出典は 1 枚あたり 6〜14 ページで、本文を取得できなかったページの内容は図から抜けた
  4. 時間の流れは読みにくい
     - 箱と線は概念どうしの関係を表すので、「受信してから削除するまで」のような手順は Action を重ねないと追えない。記事でも手順は番号付きの箇条書きで補った
- 使うべきとき
  - 別名や同じ名前の別物が多い領域を、初めて学ぶとき(Git、AWS)
  - 答えたい問いが決まっていて、その答えに要る概念の関係を確かめたいとき
- 向かないとき
  - サービスの選定や設計の判断を決めたいとき。判断基準は図の外で考える必要がある
  - 領域全体を一覧したいとき、手順を覚えたいとき

## Git の用語

### この図で答える問い

1. `git reset --soft / --mixed / --hard` はそれぞれ何を書き換えるか
2. index・staging area・cache は同じものか
3. detached HEAD でコミットすると、ブランチはどうなるか

### 別名を 1 つにまとめる

Git では同じものに名前が複数付いています。index はその代表で、マニュアルの中だけで 5 通りに書かれています。

| 書かれ方 | 出典 |
| --- | --- |
| index | gitglossary(7)、git-add(1) |
| staging area | git-commit(1)、git-diff(1) |
| cache | gitglossary(7)(「index の旧称」) |
| `--cached` | git-diff(1) などのオプション名 |
| `--staged` | git-diff(1)(「`--cached` の別名」) |

図ではこの 5 つを index という 1 つの箱にまとめ、残りは別名として箱の詳細に出典付きで残しました。逆に `HEAD`(大文字)と `head`(小文字)は名前が似ていても別の概念なので、別の箱にしています。HEAD は「現在のブランチヘッドを指す symref」で、head は「ブランチの先端を指す ref」です。

### reset の 3 モードを図で追う

1 つ目の問い「`git reset --soft / --mixed / --hard` はそれぞれ何を書き換えるか」には、git-reset(1) の状態表がそのまま答えます。

| モード | ブランチヘッド | index | 作業ツリー |
| --- | --- | --- | --- |
| `--soft` | 指定コミットへ動く | そのまま | そのまま |
| `--mixed`(既定) | 指定コミットへ動く | 指定コミットの tree に戻る | そのまま |
| `--hard` | 指定コミットへ動く | 指定コミットの tree に戻る | 指定コミットの tree に戻る |

3 モードとも、動かす前の先端を ORIG_HEAD に記録します。図で Action を重ねると、`--soft` から出る線はブランチヘッドと ORIG_HEAD の 2 本、`--hard` からは作業ツリーまでの 4 本になります。表の右へ行くほど書き換える範囲が広がることを、線の本数で確かめられます。

### この図で答える問い

1. プライベートサブネットの ECS タスク(Fargate)は、どの経路で S3 に届くか
2. セキュリティグループとネットワーク ACL は何が違うか
3. パブリックサブネットとプライベートサブネットを分けるものは何か

### 同じ名前、違う名前

| 名前 | 図での扱い | 出典 |
| --- | --- | --- |
| ENI / ネットワークインターフェイス | 同じもの。コンソールと API の呼び名が network interface | using-eni |
| NAT ゲートウェイ / NAT インスタンス | 別物。両方を「NAT デバイス」の下に置いた | vpc-nat-comparison |
| VPC エンドポイント / PrivateLink | 別物。インターフェイス型は PrivateLink を使い、ゲートウェイ型は使わない | gateway-endpoints |
| パブリックサブネット / プライベートサブネット | 別の種類のリソースではない。ルートテーブルの中身で呼び分ける | configure-subnets |

最後の行が 3 つ目の問いの答えです。関連付けたルートテーブルにインターネットゲートウェイへのルートがあればパブリック、なければプライベートと呼びます。図ではサブネットとルートテーブルの間の線で、この呼び分けを追えます。

### S3 へ届く 2 つの経路

1. NAT ゲートウェイ経由
   - ルートテーブルで 0.0.0.0/0 を NAT ゲートウェイに向ける。NAT ゲートウェイはパブリックサブネットにあり、インターネットゲートウェイを通って S3 の公開エンドポイントに届く
2. ゲートウェイ型 VPC エンドポイント経由
   - エンドポイントを作ると、S3 のプレフィックスリスト宛てのルートがルートテーブルに入る。最長一致で 0.0.0.0/0 より優先されるので、同じリージョンの S3 宛てはエンドポイントを通る
   - ゲートウェイ型が使えるのは S3 と DynamoDB だけ

どちらの経路でも、セキュリティグループとネットワーク ACL が S3 宛ての通信を許可している必要があります。

### セキュリティグループとネットワーク ACL

| | セキュリティグループ | ネットワーク ACL |
| --- | --- | --- |
| 付く先 | ENI(インスタンス) | サブネット |
| 持てるルール | 許可だけ | 許可と拒否 |
| 評価のしかた | 全ルールを見てから判断 | 番号の小さい順に見て、最初に一致したもので決める |
| 戻りの通信 | 自動で通す(ステートフル) | 明示的に許可が要る(ステートレス) |

## AWS の非同期メッセージング(SNS・SQS・EventBridge)

SNS と SQS は、BASE で[顧客管理システムを非同期化](https://devblog.thebase.in/entry/2021/12/02/110000)したときに使ったサービスです。

### この図で答える問い

1. SNS と SQS をどう組むとファンアウトになるか
2. 処理に失敗したメッセージはどこへ行くか
3. EventBridge と SNS はどう使い分けるか

2 つ目の問いは、Action を重ねて、受信してから削除するまでの流れを追うとたどれます。

### 同じ名前で別のもの

「リドライブポリシー」は SQS と SNS の両方に出てくる名前ですが、付く先も中身も違います。図では 2 つの箱に分けました。

| | SQS のリドライブポリシー | SNS のリドライブポリシー |
| --- | --- | --- |
| 付く先 | 送信元の SQS キュー | SNS のサブスクリプション |
| 持つ設定 | 移動先の DLQ と maxReceiveCount | 移動先の DLQ(deadLetterTargetArn)だけ |
| DLQ へ移る条件 | 受信回数が maxReceiveCount を超えた | サブスクライバに配信できなかった |

逆に、名前が違っても同じものとしてまとめたものもあります。

- EventBridge と CloudWatch Events は同じサービスです。EventBridge のガイドに「formerly known as CloudWatch Events」とあります
- デッドレターキュー・DLQ・dead-letter queue は同じ概念です。SNS の DLQ も、実体は普通の SQS キューです

### 失敗したメッセージの行き先

1. コンシューマがメッセージを受信すると、可視性タイムアウト(既定 30 秒)のあいだ他のコンシューマから見えなくなる
2. その間に削除されなければ、メッセージは見える状態に戻り、また受信される
3. リドライブポリシーがあれば、受信回数が maxReceiveCount を超えたメッセージは DLQ へ移る

SNS 側では、配信できなかったメッセージはサブスクリプションのリドライブポリシーが指す DLQ に入ります。DLQ が無ければ捨てられます。

## 作り方と限界

3 枚とも同じ手順で作りました。Git の図を例にすると次のとおりです。

1. 図で答える問いを 3 つ決めた(reset の 3 モード、index の別名、detached HEAD でのコミット)
2. `man gitglossary` などのマニュアルから、問いに必要な概念・関係・コマンドを抜き出した。出典は gitglossary(7)・git-reset(1)・git-diff(1)・git-add(1)・git-commit(1)・git-switch(1) の 6 つ
3. 別名をまとめ、まとめた理由を「ソース」タブの名寄せメモに書いた
4. skill の描画テンプレートで HTML にした。抽出日は 2026-10-18

- 出典は実際に開いたマニュアルと公式ドキュメントで、一覧はそれぞれの図の「ソース」タブにあります。抽出日は 2026-10-18 です
- VPC の図
  - 「サブネットの CIDR は VPC の CIDR の範囲内」は、原文に直接の記述が見つからず、サブネットの定義から導きました。その関係の線に推定と注記しています
  - Transit Gateway・VPC ピアリング・IPv6 は問いに要らないので外しました
- 非同期メッセージングの図
  - 3 つ目の問いは「一部だけ答えられる」としました。公式の選び方ガイドには、SNS はプッシュ型の pub/sub でファンアウト通知向け、EventBridge はルールでイベントを照合してターゲットへ送る型、という比較表があります。ただ、個別のケースでどちらを選ぶかの判断基準までは書かれていません
  - 「受信するたびに受信回数が 1 増える」は、属性名(ApproximateReceiveCount)と maxReceiveCount の説明から推した整理で、図では推定と印を付けています
  - SNS に送信を許可する SQS キューのアクセスポリシーは、該当ページの本文を取得できなかったので図に入れていません
- Git の図
  - pack ファイル・merge 中の多段 index・submodule・`git worktree` は問いに要らないので外しました
