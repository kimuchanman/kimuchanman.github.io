### この図で答える問い

1. プライベートサブネットの ECS タスク(Fargate)は、どの経路で S3 に届くか
2. セキュリティグループとネットワーク ACL は何が違うか
3. パブリックサブネットとプライベートサブネットを分けるものは何か

### 同じ名前、違う名前

| 名前 | 図での扱い | 出典 |
| --- | --- | --- |
| ENI / ネットワークインターフェイス | 同じもの。コンソールと API の呼び名が network interface | using-eni |
| NAT ゲートウェイ / NAT インスタンス | 別物。両方を「NAT デバイス」の下に置いた | vpc-nat-comparison |
| VPC エンドポイント / PrivateLink | 別物。インターフェイス型は PrivateLink を使い、ゲートウェイ型は使わない | gateway-endpoints |
| パブリックサブネット / プライベートサブネット | 別の種類のリソースではない。ルートテーブルの中身で呼び分ける | configure-subnets |

最後の行が 3 つ目の問いの答えです。関連付けたルートテーブルにインターネットゲートウェイへのルートがあればパブリック、なければプライベートと呼びます。図ではサブネットとルートテーブルの間の線で、この呼び分けを追えます。

### S3 へ届く 2 つの経路

1. NAT ゲートウェイ経由
   - ルートテーブルで 0.0.0.0/0 を NAT ゲートウェイに向ける。NAT ゲートウェイはパブリックサブネットにあり、インターネットゲートウェイを通って S3 の公開エンドポイントに届く
2. ゲートウェイ型 VPC エンドポイント経由
   - エンドポイントを作ると、S3 のプレフィックスリスト宛てのルートがルートテーブルに入る。最長一致で 0.0.0.0/0 より優先されるので、同じリージョンの S3 宛てはエンドポイントを通る
   - ゲートウェイ型が使えるのは S3 と DynamoDB だけ

どちらの経路でも、セキュリティグループとネットワーク ACL が S3 宛ての通信を許可している必要があります。

### セキュリティグループとネットワーク ACL

| | セキュリティグループ | ネットワーク ACL |
| --- | --- | --- |
| 付く先 | ENI(インスタンス) | サブネット |
| 持てるルール | 許可だけ | 許可と拒否 |
| 評価のしかた | 全ルールを見てから判断 | 番号の小さい順に見て、最初に一致したもので決める |
| 戻りの通信 | 自動で通す(ステートフル) | 明示的に許可が要る(ステートレス) |

## 非同期メッセージング(SNS・SQS・EventBridge)

SNS と SQS は、BASE で[顧客管理システムを非同期化](https://devblog.thebase.in/entry/2021/12/02/110000)したときに使ったサービスです。

### この図で答える問い

1. SNS と SQS をどう組むとファンアウトになるか
2. 処理に失敗したメッセージはどこへ行くか
3. EventBridge と SNS はどう使い分けるか

2 つ目の問いは、Action を重ねて、受信してから削除するまでの流れを追うとたどれます。

### 同じ名前で別のもの

「リドライブポリシー」は SQS と SNS の両方に出てくる名前ですが、付く先も中身も違います。図では 2 つの箱に分けました。

| | SQS のリドライブポリシー | SNS のリドライブポリシー |
| --- | --- | --- |
| 付く先 | 送信元の SQS キュー | SNS のサブスクリプション |
| 持つ設定 | 移動先の DLQ と maxReceiveCount | 移動先の DLQ(deadLetterTargetArn)だけ |
| DLQ へ移る条件 | 受信回数が maxReceiveCount を超えた | サブスクライバに配信できなかった |

逆に、名前が違っても同じものとしてまとめたものもあります。

- EventBridge と CloudWatch Events は同じサービスです。EventBridge のガイドに「formerly known as CloudWatch Events」とあります
- デッドレターキュー・DLQ・dead-letter queue は同じ概念です。SNS の DLQ も、実体は普通の SQS キューです

### 失敗したメッセージの行き先

1. コンシューマがメッセージを受信すると、可視性タイムアウト(既定 30 秒)のあいだ他のコンシューマから見えなくなる
2. その間に削除されなければ、メッセージは見える状態に戻り、また受信される
3. リドライブポリシーがあれば、受信回数が maxReceiveCount を超えたメッセージは DLQ へ移る

SNS 側では、配信できなかったメッセージはサブスクリプションのリドライブポリシーが指す DLQ に入ります。DLQ が無ければ捨てられます。

## 作り方と限界

- 出典は実際に開いた公式ドキュメントで、一覧はそれぞれの図の「ソース」タブにあります。抽出日は 2026-10-18 です
- VPC の図
  - 「サブネットの CIDR は VPC の CIDR の範囲内」は、原文に直接の記述が見つからず、サブネットの定義から導きました。その関係の線に推定と注記しています
  - Transit Gateway・VPC ピアリング・IPv6 は問いに要らないので外しました
- 非同期メッセージングの図
  - 3 つ目の問いは「一部だけ答えられる」としました。公式の選び方ガイドには、SNS はプッシュ型の pub/sub でファンアウト通知向け、EventBridge はルールでイベントを照合してターゲットへ送る型、という比較表があります。ただ、個別のケースでどちらを選ぶかの判断基準までは書かれていません
  - 「受信するたびに受信回数が 1 増える」は、属性名(ApproximateReceiveCount)と maxReceiveCount の説明から推した整理で、図では推定と印を付けています
  - SNS に送信を許可する SQS キューのアクセスポリシーは、該当ページの本文を取得できなかったので図に入れていません
